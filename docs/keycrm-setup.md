# Ручне створення замовлень KeyCRM

Кнопка доступна в адміністративному розділі «Замовлення», під сумою готового чека. Оформлення кошика лише зберігає чек, як і раніше. Жоден ефект, таймер, тригер чи перевірка стану не створює замовлення в CRM.

## Стан поточного розгортання

Міграцію `20261002201320_keycrm_order_exports` застосовано та записано в історію Supabase. Функцію `keycrm-orders` розгорнуто з перевіркою JWT; читання стану для поточного адміністратора повертає HTTP 200. Повторно застосовувати цю міграцію в поточному проєкті не потрібно. Для нових ручних спроб: джерело — **51**, відповідальний менеджер — **33**, email покупця — **`b@b.ua`**. Вхід залишається за телефоном.

Початковий ключ KeyCRM із локального довідкового файлу повертав HTTP 401. Користувач оновив `KEYCRM_API_KEY` у Supabase Secrets; його наступна ручна спроба для чека №941 пройшла отримання цін і завершилася HTTP 422 на створенні замовлення. Збережений стан — `failed`, CRM-ID не отримано. Точна відповідь тієї спроби не збереглася у першій версії обробника; початкова підказка про покупця була загальною, а не підтвердженою причиною. Обробник оновлено для збереження конкретних помилок API під час наступного ручного натискання. Автоматичні повторні POST для діагностики не виконувалися.

Наступна ручна спроба підтвердила конкретне обмеження API: `buyer.email` та `buyer.phone` повернули помилки `required when none of buyer.id / buyer.full name / ... are present`. Потрібне щонайменше одне з `buyer.id`, `buyer.full_name`, `buyer.phone`, `buyer.email`; запит з усіма порожніми даними покупця відхиляється. Користувач погодив постійне значення **`buyer.email: "b@b.ua"`**. `buyer.full_name` та `buyer.phone` залишаються `null`; ім’я та контакти із локального чека не підставляються. Цей email передається відразу в одному POST після ручного натискання, а не додається автоматичним повтором після помилки.

Уточнення від 03.10.2026: `source_id` змінено з 1 на 51; відповідальний менеджер задається через поле запиту `manager_id: 33` (у відповіді CRM він може бути вкладеним `manager.id`); email змінено з `a@a.ua` на `b@b.ua`. Зміни застосовуються до майбутніх ручних спроб; збережені запити та вже створені замовлення не переписуються. Міграція бази та зміна Secrets не потрібні.

## Налаштування Supabase

1. Застосуйте `supabase/migrations/20261002201320_keycrm_order_exports.sql` через SQL Editor або звичний процес міграцій. Міграція розрахована на числовий `public.orders.id`, наявні `orders` та `app_settings` і не змінює чеки, товари чи їхні RLS-політики.
2. Вхід залишається **за телефоном, без email, пароля та PIN**, за прямим уточненням користувача. Міграція одноразово переносить номери адміністраторів із `app_settings` (`catalog.adminPhones` або `admin_phones`) до закритої таблиці `keycrm_admins`. Перевірте список у SQL Editor. Якщо номер був лише у локальних налаштуваннях/початковій конфігурації застосунку, додайте його вручну:

   ```sql
   insert into public.keycrm_admins(phone)
   values ('+380XXXXXXXXX')
   on conflict do nothing;
   ```

   Подальша зміна публічних `app_settings` **не** надає доступ до CRM автоматично. Для нового адміністратора оновіть також закритий список через SQL Editor; для відкликання видаліть номер із `keycrm_admins`. Це не додає нового екрана входу в браузері чи Telegram.

   **Узгоджене обмеження:** номер не підтверджується паролем/OTP. Людина, яка знає дозволений номер, може відтворити запит від його імені. Перевірка списку не є надійним підтвердженням особи. Значення `actor_phone`/`reviewed_by_phone` фіксують заявлений номер, а не криптографічно підтвердженого користувача.
3. У **Edge Functions → Secrets** додайте `KEYCRM_API_KEY`. Ключ читається лише на сервері через `Deno.env.get('KEYCRM_API_KEY')`. Не створюйте змінну з префіксом `VITE_` і не додавайте ключ у код, SQL, payload чи логи. `SUPABASE_SERVICE_ROLE_KEY` і `SUPABASE_URL` надаються середовищем Supabase автоматично.
4. Розгорніть функцію **keycrm-orders** з її `index.ts` та `core.mjs`. З Supabase CLI:

   ```sh
   supabase functions deploy keycrm-orders --project-ref YOUR_PROJECT_REF
   ```

   У `supabase/config.toml` ввімкнено gateway JWT: браузер використовує наявний anon JWT проєкту. **Кожен GET/POST додатково звіряє `x-admin-phone` із закритою таблицею `keycrm_admins`**. Публічний anon key не є секретом адміністратора. Не відключайте серверну перевірку номера.
5. Запустіть `npm run dev -- --host 127.0.0.1`, відкрийте адміністративний розділ «Замовлення», натисніть «Оновити стан CRM». Поки міграція, функція, права чи секрет не налаштовані, створення недоступне, а первісні чеки залишаються видимими.

## Локальний ключ і перевірки

Локальний серверний файл `supabase/.env.keycrm.local` і папка `замовлення/` ігноруються Git та закриті для Vite. Якщо файл ключа підготовлено з локальних матеріалів, він не завантажується в Supabase автоматично і не використовується браузером. Його можна передати локальному середовищу Edge Functions:

```sh
supabase functions serve keycrm-orders --env-file supabase/.env.keycrm.local
```

Це потребує встановлених Supabase CLI, Docker та запущеного локального Supabase (`supabase start`), із застосованою схемою магазину й міграцією CRM. Для повністю локального запуску змініть `.env.local` на URL/anon key локального Supabase. `npm run dev` сам по собі запускає інтерфейс, який звертається до Supabase, зазначеного в `.env.local`.

`npm test` перевіряє кошик, ціни, навігацію та сценарії CRM із підставними HTTP-відповідями, без справжніх замовлень. `npm run build` перевіряє виробничу збірку. Окремо перевірте міграцію у тестовому Supabase перед застосуванням до робочої бази.

## Контракт передачі

- Браузер передає тільки ID локального чека та дію. Сервер читає `orders.items`: `sku` → SKU без втрати початкових нулів; `name` → назва; `qty` → кількість. Збережені `price` і `orders.total` не використовуються для CRM.
- Після натискання сервер отримує **всі** актуальні ціни продажу з `GET /offers?filter[sku]=...`: точний SKU, `data[].price`, пакети до 50 SKU з пагінацією. Відсутній SKU, дубль, некоректна ціна чи помилка читання блокують увесь POST. Резервних цін і повторного застосування локальних знижок немає.
- `POST /order` отримує `source_id: 51`, `manager_id: 33`, `manager_comment: "⌛️⌛️💴💵💶💷"`, `discount_percent: 50`, `buyer: { full_name: null, phone: null, email: "b@b.ua" }`, товари з актуальними цінами. `source_uuid`, `ordered_at`, дані покупця з застосунку, Telegram, платежі й доставка не передаються. Дату та внутрішній ID створює CRM.
- За уточненням від 03.10.2026, локальний чек уже містить знижку бренду. Його ціни й суму не зменшуємо повторно. У CRM передаємо повну актуальну `offers.price` та одну фіксовану знижку **50% на рівні замовлення**, без знижок на рівні товарів. Значення 50 є окремою погодженою умовою експорту й не обчислюється зі збереженого чека або налаштувань бренду. Фактичну суму читаємо з `grand_total`; уже створені CRM-замовлення не перераховуються.
- Обов’язковий атрибут покупця заповнюється погодженим постійним email `b@b.ua`. При HTTP 422 показується конкретна помилка; автоматичних підстановок інших даних покупця чи повторів POST немає.
- HTTP 422 сам по собі не визначає проблемне поле. Зберігається і показується обмежений за довжиною текст `errors`/`message`/`error` із фактичної відповіді KeyCRM, із приховуванням ключів і токенів. Для старих спроб, де відповідь була втрачена, причина не вигадується. Отримання нової відповіді можливе лише після нового ручного натискання; автоматичного діагностичного POST немає.
- Первісний чек не змінюється. Після підтвердженого успіху окремо показуються CRM-ID та фактичний `grand_total` з відповіді CRM. Якщо фактична сума відсутня, потрібна перевірка.

## Стани та відновлення

У `keycrm_order_exports` один запис на локальний чек. Атомарна функція `claim_keycrm_order` дозволяє почати тільки нову спробу або повторити визначено відхилену. Одночасні натискання з різних пристроїв отримують наявний стан. Усі таблиці/функції інтеграції доступні лише service role; `crm_id` також унікальний.

| Стан | Поведінка |
| --- | --- |
| `preflight` | Ціни перевіряються, POST ще не починався. Застаріла підготовка після 2 хв може перейти в `failed` під час читання стану; старий виконавець уже не пройде перевірку стану/ID спроби. |
| `posting` | Payload і стан підтверджено збережені **до** єдиного POST. Нове створення заблоковане. |
| `created` | Коректний CRM-ID та сума отримані й результат підтверджено збережений у Supabase. |
| `failed` | POST не виконувався або отримано визначене відхилення API без CRM-ID. Повторити можна лише новим натисканням; ціни отримуються заново. |
| `needs_review` | Втрачена відповідь POST, HTTP 5xx, неочікувана відповідь, успішний HTTP без ID/суми або збій збереження. Повторне створення заборонене. |

Непідтверджений `posting` після 2 хв стає `needs_review` під час перевірки стану, але ніколи не розблоковується за таймером. Якщо після POST база недоступна, збережений `posting` продовжує блокувати наступні спроби. Браузер також залишає локальну позначку до запиту: втрата його відповіді не дає можливості повторити створення після перезавантаження сторінки. Невідома спроба без серверного запису вимагає розслідування; не видаляйте позначку, поки невідомо, чи виконався запит.

«Оновити стан CRM» не робить POST до KeyCRM. Для невизначеного результату адміністратор знаходить замовлення в CRM, вводить його ID та підтверджує відповідність чеку. «Перевірити та прив’язати CRM-ID» виконує тільки GET: перевіряє ID, джерело зі збереженого `request_payload.source_id`, SKU, кількості та ціни і зберігає результат у Supabase. Це зберігає можливість перевірки попередніх спроб із джерелом №1 після переходу нових спроб на №51. Якщо джерело у збереженому запиті відсутнє чи некоректне, прив’язування заборонене. Якщо замовлення не знайдено, стан залишається заблокованим; автоматичного повторного створення або скидання блокування немає.

Без `source_uuid` зовнішня ідемпотентність API не використовується: окремий CRM-ID кожного нового замовлення сам по собі не запобігає двом однаковим замовленням. Локальне блокування захищає передачу одного чека через цей застосунок, але не створення з n8n/інших систем та не ручне видалення стану інтеграції. При ручній прив’язці однакові набори товарів не доводять тотожність замовлень, тому потрібна перевірка адміністратором.

KeyCRM допускає 20 запитів/хв на ключ. База розділяє слоти з інтервалом 3,1 с між виконавцями цього застосунку; запити n8n та інших систем теж входять у зовнішню квоту. Автоматичних повторів POST, черг і фонових створень немає.

## Повідомлення про видачу

Поруч із кожним чеком на екранах від 960 px, а на менших екранах під ним показується блок «Повідомлення покупцеві». Кнопка «Редагувати шаблон» відкриває спільний редактор. «Зберегти шаблон» зберігає `orderIssueTemplate` у наявному `app_settings` → `key: catalog`; окрема міграція не потрібна. Наявні налаштування й невідомі поля зберігаються. До підтвердження запису новий текст не застосовується; помилка залишає чернетку в редакторі. Збереження налаштувань виконується послідовно, щоб старий запит не перезаписав новий шаблон.

Поля автоматичної підстановки:

| Поле | Значення |
| --- | --- |
| `{{сума_чека}}` | Первісне `orders.total`, уже зі знижкою застосунку; без перерахунку. |
| `{{сума_CRM}}` | Підтверджене `keycrm_order_exports.crm_total`, отримане з `grand_total` CRM. |
| `{{номер_CRM}}` | Підтверджений `keycrm_order_exports.crm_id` для цього чека, використовується як призначення. |

Початковий шаблон:

```text
Видача замовлень
з 16:00 до 18:00
(оформлених до 15:00)
-               -               -
{{сума_чека}} : сума чека
{{сума_CRM}} : сума CRM
{{номер_CRM}} : призначення
-               -               -
🫆UA903052990000026005025017139
-               -               -
ТИЩЕНКО В.О.
ІПН/ЄДРПОУ 2143302639
```

Обидві суми показуються окремо, навіть коли збігаються. Для попередніх CRM-замовлень показується їхня збережена фактична сума. Реквізити та години можна редагувати у шаблоні; всі три поля підстановки обов’язкові. «Копіювати весь текст» доступна лише після стану `created` із коректними сумами й CRM-ID. Копіюється звичайний багаторядковий текст; для WebView без Clipboard API передбачено копіювання через виділення. При помилці пропонується виділити текст вручну. Редактор, копіювання й оновлення стану не викликають створення замовлення.
